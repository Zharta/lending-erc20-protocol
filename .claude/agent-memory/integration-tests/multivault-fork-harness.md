Durable gotchas for `tests/p2p_erc20_multivault/integration/` fork tests (block 24541820, mainnet).

**Capture events immediately after the state-changing call.**
boa's `contract.get_logs()` (used by `get_last_event`) returns logs from the *most recent call to that contract instance*. Any later getter call to the SAME contract (e.g. `p2p.loans(...)`, `p2p.protocol_upfront_fee()`, `p2p.commited_liquidity(...)`) clears the log buffer, and `get_last_event` then returns `IndexError: list index out of range`.
How to apply: in a test, grab all `get_last_event(p2p, ...)` results into locals right after the `create_leveraged_loan`/`create_loan`/`redeem`/`settle_loan` call, *before* any other call to that contract. Calls to other contracts (usdc/mfone/oracle) are fine.

**Facet-emitted events must be registered in the conftest `log_stuff` injection.**
`integration/conftest.py` appends a dummy `log_stuff()` to the main contract source so boa can decode events that are only emitted via delegatecall from facets (Loan/Refinance/Liquidation). An event declared in main but emitted only by a facet (e.g. `LeveragedLoanCreated`, `LoanCreated`, `LoanReplaced`) is NOT decodable unless it appears in `log_stuff`. Symptom: `get_logs()` returns `[]` / empty even though the tx emitted the event.
How to apply: when a test reads a facet-emitted event, ensure it's in `log_stuff` with the exact current field order. Vyper enforces event keys in declaration order, so a stale field list (e.g. missing `create_time` between `maturity` and `start_time`) raises `InvalidAttribute` at contract load and blocks the WHOLE dir.

**Midas instant redeem is size-limited at this block; instant mint is not.**
`P2PLendingVaultMidas.mint_sync` -> Midas `depositInstant` handles large amounts (minted ~94k mfone from 100k USDC fine). But `redeem_sync` -> RedemptionVault `redeemInstant` reverts ("external call failed") for large amounts (~47k mfone). Keep redeem-path lifecycle tests small (hundreds of mfone, e.g. mint_spend ~260 USDC -> ~245 mfone -> redeem ~122). The retired proxy lifecycle test redeemed ~125 mfone.

**Leveraged loan flow shape (create_leveraged_loan, MINT_SYNC / Midas vault).**
Borrower supplies a USDC *margin*, not collateral; ALL collateral is minted. Both lender and borrower `approve` the LENDING CONTRACT (no proxy, no Balancer flash loan). lender deploys `principal - origination_fee` into the loan vault; borrower deploys `mint_spend - (principal - origination_fee)`. mint_sync spends the full mint_spend so refund is 0 -> `new_principal == principal` for both fixed and flexible offers in the happy path. The loan's `collateral_amount` is the ACTUAL minted amount (read it as `mfone.balanceOf(vault_addr)` after the call, an independent ground-truth). `loan.initial_ltv` = `max_iltv` for a fixed offer with max_iltv set, else `calc_ltv(principal, min_collateral_amount)` when `max_iltv == 0`. The market must be deployed with the Midas vault impl so `vault_capabilities` (immutable, read once at __init__) includes MINT_SYNC. The borrower's *next* vault (the CREATE2 addr returned by `wallet_to_vault(borrower)` at vault_count==0) must be Midas GREENLISTED before the call.

**ACRED SecuritizeSwap economics at block 24541820 (test_loop_acred, create_leveraged_loan).**
ACRED (0x17418038ecF73BA4026c4f428547BF099706F27B) and USDC are both 6-dec. oracle_acred_usd (0xD6Bc...d51C) has 8 decimals, price ~1096.64 USDC/ACRED. The on-ramp swap address is `acred_ds_token.getDSService(1<<14)` (query the DS TOKEN, not securitize_registry — the registry's getDSService returns 0x0). At this block the swap has ZERO fee and its rate EXACTLY equals the oracle: `calculateDsTokenAmount(usdc) == usdc * price_den // price_num`, and the inverse (USDC to buy N ACRED) `== N * price_num // price_den` round-trips to N exactly. So in the D2 sync leveraged flow, `minted == mint_spend*price_den//price_num` with refund 0 (`usdc.balanceOf(vault)==0` after). Sizing used: principal=sum([70000,49000,34300,24000,17000])e6=194300e6, collateral=sum([94,66,46,32,23])e6=261e6 ACRED, mint_spend=261e6*price_num//price_den≈286222e6, realized LTV≈6788bps (use max_iltv=7000, min_collateral_out=collateral*99//100). The Securitize MV vault (P2PLendingVaultSecuritizeMV, MINT_SYNC|REDEEM_MANUAL) needs NO greenlist step (unlike Midas) — `_create_new_vault` registers it via the registrar_connector before mint_sync's swap. `redeem()`→`redeem_manual` transfers redeemed ACRED to redemption_addr (redemption_wallet) with no on-chain USDC payout; simulate off-chain proceeds by `usdc.transfer(vault, collateral_to_redeem*price_num//price_den, sender=redemption_wallet)` before settle. `deposit_vault` arg to create_leveraged_loan is ignored by Securitize mint_sync — pass empty(address). The `securitize_vault_impl` fixture in integration/conftest.py MUST return the MV vault (`securitize_mv_vault_contract_def.deploy()`) for `p2p_usdc_acred` to init (immutable vault_capabilities read at __init__ needs `capabilities()`).

**Fork fixture USDC funding contention.** integration/conftest.py's `usdc` fixture gives EACH of `accounts` 1e12 USDC; `redemption_wallet` drains accounts[0] by 1e12 and `lender_funds` uses owner. Any new autouse borrower-USDC-margin fixture must pull from a DIFFERENT account (used accounts[1]) or it collides with redemption_wallet on accounts[0] ("transfer amount exceeds balance").

**REDEEM_SYNC vaults settle atomically via redeem_and_settle, NOT two-phase (feat/despxa-loop, 2026-07-02).**
For REDEEM_SYNC markets (Midas mfone), `P2PLendingMultiVaultErc20.redeem(loan, residual)` now REVERTS `"use redeem_and_settle"` (it only serves deferred REDEEM_MANUAL/REDEEM_ASYNC now). The atomic entry point is `redeem_and_settle(loan, residual_collateral, sender=borrower)` (facet: P2PLendingMultiVaultLoan.redeem_and_settle): converts `collateral_amount - residual` mfone->USDC via `redeem_sync` AND settles in the SAME tx. No redeem_start state, no LoanCollateralRedeemStarted, no settle_loan follow-up, NO owner-signed RedeemResult. Distribution mirrors settle_loan (lender=amount+interest-protocol_fee, protocol=fee, borrower tops up shortfall / gets surplus, residual collateral returned, loan cleared, LoanPaid emitted). REDEEM_MANUAL (acred, test_loop_acred/test_transfer) is UNAFFECTED — still two-phase redeem()+settle_loan.
Testing gotcha: the redeem proceeds (`in_vault_payment_token`) are net of the Midas redeem fee and NOT independently computable, and being atomic you cannot observe them mid-tx like the old two-phase test did. Measure them as ground truth via USDC conservation: `measured_redeemed = lender_delta + borrower_delta + protocol_delta` (real balance deltas; borrower delta is signed and nets the shortfall top-up) == `event.in_vault_payment_token`, and bound `0 < measured_redeemed <= oracle_redeem_usdc`. Lender payment (=principal when interest 0), protocol fee, residual collateral to borrower, loan cleared, liquidity->0 stay exact/independent. With apr=0 + no time-travel + fee net of principal, the borrower ALWAYS tops up a small shortfall, so `usdc.approve(p2p, loan.amount+interest, sender=borrower)` an upper-bound allowance BEFORE the atomic call (exact top-up unknown pre-tx).

**create_time field (resolved 2026-06-26 on feat/despxa-loop):** the MultiVault `Loan` struct has `create_time` between `maturity` and `start_time`; the shared `tests/p2p_erc20_multivault/conftest_base.py` `Loan` NamedTuple + `compute_loan_hash`/`compute_loan_id` already include it. The contract sets `create_time=block.timestamp` in `_create_loan` (P2PLendingMultiVaultLoan.vy) AND in both refinance paths (P2PLendingMultiVaultRefinance.vy replace/replace_lender), so for any freshly created OR replaced loan `create_time == start_time == accrual_start_time`. Every integration test that builds an expected `Loan(...)` must set `create_time` to the same value as `start_time` (=`now` for fresh, =`replace_timestamp` for the new loan after a replace). All 14 integration tests pass with this. `replace_namedtuple_field`-derived loans (add/remove collateral, redeemed/transferred) inherit create_time automatically.
